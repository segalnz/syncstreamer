2. `NetworkReceiver.cpp:63`: `g_rx_packets++;`

**Fix**: Replace `g_variable++` with `g_variable += 1` (compound assignment does not trigger

**Verification**: Build should be warning-clean for these two lines.

## Symptom
Continuous static/fuzz overlaid on sound, not correlated with seq gaps, disappears during silence between tracks. Like losing lock and not recovering.

## Change 1: PLL feed-forward (`SyncController.cpp`)

**Current**: Pure feedback PLL:
```c
float raw_ppm = g_filtered_err * 0.1f;
```

**Change**: Add feed-forward term from server clock offset drift:
```c
// Instantaneous PPM from offset change over this tick interval (200 ms).
int64_t off = g_offset_us;
int64_t dt_us = esp_timer_get_time() - s_last_ff_time;
if (dt_us > 0 && dt_us < 500000) {     // sanity: skip first tick or large gaps
    float inst_ppm = (float)(off - s_last_ff_offset) * 1e6f / (float)dt_us;
    s_ff_ppm += 0.4f * (inst_ppm - s_ff_ppm);   // IIR low-pass, α=0.4
}
s_last_ff_offset = off;
s_last_ff_time   = esp_timer_get_time();

// Combine feed-forward + feedback.
// Reset feed-forward when occupancy error exceeds ±50 % of target
// (transient network jitter spikes are not integrated).
float fb_ppm = g_filtered_err * 0.1f;
float raw_ppm = (err > -1440 && err < 1440) ? (s_ff_ppm + fb_ppm) : fb_ppm;
```

**Rationale**: Feed-forward directly compensates the local-crystal vs server-clock frequency mismatch without waiting for buffer occupancy to change. Eliminates the systematic rate error that the feedback loop would otherwise have to integrate out — the root cause of the PLL oscillating and producing "fuzzy" audio.

**Needs**: `#include "OffsetEstimator.h"` and `extern volatile int64_t g_offset_us` (already declared).

## Change 2: `offset_estimator_reset()` on stream start (`OffsetEstimator.h/cpp`, `NetworkReceiver.cpp`)

**Current**: `network_receiver_stream_reset()` resets only sequence tracking, gap/dropout counters.

**Change**: Add `offset_estimator_reset()` call to `network_receiver_stream_reset()`. Implement it in `OffsetEstimator.cpp` (already exists in the fork, just add to this project).

**Rationale**: Stale offset samples from the previous stream in the ring buffer produce a wrong `g_offset_us` on the first few packets of a new stream. For the PLL feed-forward (Change 1), a stale offset directly feeds a wrong `inst_ppm`, which causes rate error until the ring refills.

## Change 3: Gap log rate limiting (`NetworkReceiver.cpp`)

**Current**: Large sequence gaps (≥10) logged immediately:
```c
if (gap >= 10) {
    log_w("wifi_rx: large seq gap %u→%u (%u lost)", expected, pkt.sequence, gap);
}
```

**Change**: Rate-limit large gap warnings to at most one per 5000 ms:
```c
if (gap >= 10) {
    static uint32_t s_last_gap_log = 0;
    uint32_t now = millis();
    if (now - s_last_gap_log >= 5000) {
        s_last_gap_log = now;
        log_w("wifi_rx: large seq gap %u→%u (%u lost)", expected, pkt.sequence, gap);
    }
}
```

**Rationale**: Serial output from high packet-loss bursts can flood the UART, competing with `log_i()` calls from other tasks and causing I2S DMA underruns (which produce zeros → pops on resume). `auto_clear=true` makes this silent but not harmless.

## Change 4: `sync_task` → core 0 (`syncstreamer.cpp`)

**Current**: `sync_task` on Core 1:
```c
xTaskCreatePinnedToCore(sync_task, "sync_ctrl", 4096, nullptr, 15, nullptr, 1);
```

**Change**: Pin to Core 0:
```c
xTaskCreatePinnedToCore(sync_task, "sync_ctrl", 4096, nullptr, 15, nullptr, 0);
```

**Rationale**: Core 1 runs `audio_out_task` (pri 22 — 48 kHz frame-by-frame), I2S DMA interrupts, `wifi_rx_task` (pri 18), and `ctrl_rx_task` (pri 16). Moving the 5 Hz PLL tick off Core 1 gives the audio output path more headroom, reducing the chance of task starvation → I2S underrun. The 5 Hz PLL is not performance-critical.

## Change 5: Raised-cosine crossfade (concealment) (`Resampler.cpp`)

**Current**: Linear ramp crossfade with `CONCEAL_FADE_FRAMES = 240` (~5 ms). Abrupt `conceal_phase` toggling from positive to negative on exit from concealment.

**Change**: Replace linear ramp with a raised-cosine (Hann) window. Precompute a 256-entry LUT at compile time. `CONCEAL_FADE_FRAMES = 480` (~10 ms).

The amplitude formula:
```
amplitude = 0.5f * (1.0f + cosf(π * t))    where t = conceal_phase / CONCEAL_FADE_FRAMES
```

With the current concealment logic that tracks:
- `conceal_phase = 0`: normal playback
- `conceal_phase` counts up during frame loss: compute `t = conceal_phase / CONCEAL_FADE_FRAMES` (clamped to 1.0)
- On first valid frame after loss: keep `conceal_phase` counting up (it already captured the gap length), but now we're fading back in — so `t` counts back down (symmetric fade)
- When `conceal_phase` reaches 0: reset amplitude to 1.0

This means a single counter, single LUT lookup, no `conceal_phase` sign toggling. The zero derivative at t=0 and t=1 eliminates corner clicks that the linear ramp produces.

**Rationale**: Linear ramp crossfade has derivative discontinuities at the fade-in/out join points, producing audible clicks on each concealment boundary. Raised-cosine (Hann window) has zero derivative at both ends. For gaps shorter than 480 frames, the cosine never reaches 0, so the fade depth is proportional to gap duration — no abrupt amplitude jump.

## New issue: intermittent static/clipping distortion after all 6 changes applied

### Symptom
- Periods of clipping-like static distortion that come and go, eventually recovering somewhat
- Mild static scattered throughout even outside the bad periods

### Root cause: feed-forward noise injection from offset-estimator step changes

The offset estimator (`OffsetEstimator.cpp`) maintains a 32-entry ring buffer and reports
`g_offset_us` as the **minimum** of all samples. This produces step-change behavior:

1. **New lower sample** → `g_offset_us` drops by up to tens of milliseconds
2. **Old minimum evicted** → `g_offset_us` jumps UP when no replacement is as low

The PLL feed-forward computes:
```
inst_ppm = (current_offset - previous_offset) × 10⁶ / 200ms
```

Each offset step of 10 ms produces `inst_ppm ≈ 50,000 ppm`. The IIR (`α=0.4`)
stores this in `s_ff_ppm` and takes ~5 seconds to decay it. Meanwhile, new steps
re-inject spikes. Although `g_rate_ppm` is delta-clamped to ±10 ppm/tick, the
internal `s_ff_ppm` oscillates between extreme values, pushing the rate to the
clamp limits each tick. The resampler follows this rate oscillation, producing
audible modulation that sounds like static/clipping.

### Change 7: Feed-forward hardening (`SyncController.cpp`) — **APPLIED, MADE IT WORSE**

Two changes to `pll_update()`:

1. **Validate `inst_ppm`** — reject values with absolute value > 500. A real
   crystal-to-crystal offset is at most ~200 ppm. Anything beyond 500 is a
   measurement artifact from the offset-estimator step change.

2. **Reduce IIR alpha from 0.4 → 0.1** — increases the feed-forward time constant
   from ~0.5 s to ~2 s (at 5 Hz), providing much stronger filtering of residual
   offset noise. The slower convergence is acceptable because the feedback loop
   handles short-term corrections.

```c
float inst_ppm = (float)(off - s_last_ff_offset) * 1e6f / (float)dt_us;
// Reject physically impossible values caused by offset-estimator step changes.
if (inst_ppm > -500.0f && inst_ppm < 500.0f) {
    s_ff_ppm += 0.1f * (inst_ppm - s_ff_ppm);
}
```

**Test result**: User reports audio is now drastically worse — "underwater" sound
with significant static, recovering somewhat but still unacceptable.

### Root cause: the Hann LUT from Change 6 is wrong

The raised-cosine LUT in `Resampler.cpp` was incorrectly computed. Verification shows:

| i | Expected (correct Hann) | Actual (in code) |
|---|------------------------|------------------|
| 0 | 65535 (100%) | 65535 ✓ |
| 128 | 32566 (50%) | 36906 (56%) ✗ |
| 255 | 0 (0%) | 10668 (16%) ✗ |

The LUT at i=255 gives 16% amplitude instead of 0%. Consequence:
- Concealment **can never fully silence** audio — minimum amplitude is ~0.16×
- The attenuation curve vs time is incorrect at every data point
- When JB underruns occur (from PLL rate oscillation), the wrong crossfade
  amplifies the distortion instead of suppressing it

### Change 8: Fix Hann LUT + restore feed-forward α=0.4 (`Resampler.cpp`, `SyncController.cpp`)

**File 1**: `Resampler.cpp` — Replace the broken `s_cos_lut[256]` with the
correctly computed Hann window LUT:

<correct LUT generated above — 256 entries, 0 at i=255, 65535 at i=0>

**File 2**: `SyncController.cpp:pll_update()` — Restore α from 0.1 → 0.4,
**keeping** the `>500` validation:

```c

if (inst_ppm > -500.0f && inst_ppm < 500.0f) {
    s_ff_ppm += 0.4f * (inst_ppm - s_ff_ppm);   // α=0.4 (restored)

```

**Rationale**: The `>500` validation correctly prevents offset-estimator step
changes from corrupting `s_ff_ppm`. With α=0.4 and validated input, the feed-forward
converges in ~2 s to the true crystal offset without amplifying noise. This
eliminates the rate oscillation that triggered JB underruns in the first place.
Combined with the correct Hann LUT, concealment events (if any) fade cleanly
to/from silence.

## Diagnostic: packet storms / missed packets / dropouts (firmware vs WiFi)

### Current architecture

**Recap of packet flow**:
- Server sends ~187.5 Hz UDP bursts (256 stereo frames × 1040 bytes) = ~195 KB/s
- Each packet arrives on Core 0 via `wifi_rx_task` (pri 18), written to JB frame-by-frame
- JB is consumed on Core 1 by `audio_out_task` (pri 22) via resampler → I2S DMA
- `sync_task` runs PLL at 5 Hz (currently on Core 1 from `main.cpp:103`)

**Task layout** (`main.cpp:98-103`):
| Task | Core | Priority | Stack |
|------|------|----------|-------|
| `wifi_rx_task` | 0 | 18 | 8192 |
| `ctrl_rx_task` | 0 | 16 | 4096 |
| `audio_out_task` | 1 | 22 | 4096 |
| `sync_task` | 1 | 15 | 4096 |

### Suspect #1: jb_write per-frame mutex (likely primary cause)

`NetworkReceiver.cpp:91-96` writes 256 frames one at a time inside `jb_write()`.
Each `jb_write()` call:
1. Takes `s_mutex` (binary semaphore)
2. Writes 4 bytes to PSRAM ring buffer
3. Updates `s_write_head`
4. Records `s_last_write_us`
5. Releases mutex
6. Calls `xSemaphoreGive()` — which checks if a higher-priority task is waiting

**256 semaphore ops per packet × 187.5 Hz = 48,000 Take/Give pairs per second.**
Each pair triggers a FreeRTOS yield check. At this rate, the overhead is substantial.

Additionally, `sync_task` (Core 1, pri 15) calls `jb_occupancy_frames()` at 5 Hz,
which takes the SAME mutex. `jb_peek()` and `jb_advance()` (Core 1, called 48k/s)
do NOT take the mutex — they assume the read head is only modified by the same task.

**Fix**: Batch the 256-frame write into one mutex-locked operation. Replace the
per-packet loop in `NetworkReceiver.cpp` with a single `jb_write_packet()` call
that takes the mutex once, writes all frames, then releases. Also remove the
redundant `s_last_write_us` update per frame (one per packet is sufficient).

### Suspect #2: MQTT publish competing with audio

`main.cpp:122` calls `status_server_loop()` which publishes MQTT every 2s.
MQTT uses TCP — if the broker connection drops, TCP reconnect holds lwIP
resources for hundreds of ms. The main loop runs at idle priority (~1), so it
can't preempt `wifi_rx_task` (pri 18). However, the TCP stack shares lwIP
resources with UDP audio sockets, so a stalled MQTT reconnect can delay
UDP packet delivery at the lwIP level.

MQTT has no sync dependency — it's one-way telemetry. We can safely skip
publishes when the audio path is under pressure.

**Fix**: In `status_server_loop()`, skip MQTT publish when JB occupancy is
below 50% of target (i.e. if `jb_occupancy_frames() < JB_TARGET_FRAMES / 2`).
This prevents MQTT TCP from consuming lwIP resources when audio packets are
already backing up.

### Suspect #3: sync_task stayed on Core 1 — FIXED (Step 10)

Our Step 5 change to `syncstreamer.cpp` had no effect because `main.cpp` creates
tasks directly and pins `sync_task` to Core 1 at line 103. The `syncstreamer.cpp`
task creation is never called by this project. `sync_task` is still on Core 1
competing with `audio_out_task`.

### Suspect #4: lwIP socket buffer

Socket receive buffer is 65536 bytes = ~63 packets = ~337ms of audio. If
`wifi_rx_task` stalls for >337ms (due to the 256 semaphore ops or other
blockage), packets overflow and seq gaps appear. At -62 dBm RSSI, the physical
layer should handle ~195 KB/s easily, so bulk loss is more likely a firmware
bottleneck than WiFi reception failure.

### Suspect #5: WiFi power-save co-existence — deferred

## New issue: first word of speech missing (TTS startup latency)

### Root cause: 200ms JB startup fill is too long for speech

When `STREAM_START` arrives, the client timeline is:
1. `ctrl_rx_task` sets `g_stream_active = true` (immediate)
2. `sync_task` at 5 Hz detects it at next tick: **up to 200ms delay**
3. `jb_sync_read_head()` discards all in-flight data, starts filling
4. Fills to `JB_STARTUP_FRAMES = 9600` frames: **another 200ms**
5. Worst-case unmute at **T+400ms** after STREAM_START

The server pre-appends silence to the TTS audio, but 400ms is enough to cover
the silence AND the first ~500ms of speech. The DAC unmutes mid-speech.

### Fix: TTS-specific startup threshold

`JitterBuffer.h` already has mode-dependent thresholds for lo/hi/crit in
`SyncController.h` — but `JB_STARTUP_FRAMES` is shared across both modes.

Add `JB_STARTUP_FRAMES_TTS = 2880` (60ms) in `JitterBuffer.h`, consistent with
TTS's existing `SC_HI_TTS = 150ms` and `SC_LO_TTS = 20ms`.

In `SyncController.cpp:state_machine_tick()`, both the ACQUIRING and REACQUIRING
transitions must use the mode-dependent threshold:

```c
uint32_t startup = (g_mode == MODE_TTS) ? JB_STARTUP_FRAMES_TTS : JB_STARTUP_FRAMES;

// ACQUIRING:
if (occ >= startup) { audio_out_unmute(); g_state = ST_LOCKED; }

// REACQUIRING:
if (occ >= startup) { audio_out_unmute(); ... g_state = ST_LOCKED; }
```

**Files**: `JitterBuffer.h` (add define), `SyncController.cpp` (use mode-dependent threshold)

## Comparison: waveshare fork vs our code (audio quality differences)

The `waveshare/` directory contains an ESP32-S3-AUDIO-Board project using a
forked syncstreamer library that reports good audio quality with the same back-end
server. Key differences found (excluding wakeword/mic):

### 1. JB ring in INTERNAL RAM vs PSRAM — likely most impactful

| | Waveshare | Ours |
|---|-----------|------|
| Allocation | `MALLOC_CAP_INTERNAL` (SRAM) | `MALLOC_CAP_SPIRAM` (PSRAM) |
| Latency | ~30 ns per access | ~120 ns per access |

The JB ring is read at 48 kHz by `audio_out_task` on Core 1. PSRAM reads/writes
are ~4× slower. The `jb_peek()` + `jb_advance()` paths are on Core 1's critical
audio path — any extra latency increases CPU time per frame, raising I2S underrun
risk. On the PCM5102A DevKit, there's plenty of internal SRAM (327 KB total; the
15.4% used = 50 KB, plus JB at 16384 × 4 bytes = 64 KB would push it to ~114 KB
still well within the 320 KB of internal SRAM before PSRAM is needed).

**Action**: Change `JitterBuffer.cpp:jb_init()` from `MALLOC_CAP_SPIRAM` to
`MALLOC_CAP_INTERNAL`. If allocation fails (shouldn't on S3 with 320 KB SRAM),
fall back to PSRAM.

### 2. PLL feed-forward uses relative drift (`offset_drift_us()`) vs absolute offset

| | Waveshare | Ours |
|---|-----------|------|
| FF input | `offset_drift_us()` = `g_offset_us - baseline` | `g_offset_us` directly |
| Reset | Baseline captured when ring first filled | `ff_reset()` zeroes everything |

`offset_drift_us()` subtracts the stream-start baseline, giving the CUMULATIVE
drift since stream start rather than absolute offset. This is a much cleaner
signal for the feed-forward PLL — it doesn't jump when the ring-buffer minimum
shifts (the absolute minimum jumps, but the drift is continuous).

**Action**: Add `offset_drift_us()` (and `s_baseline` capture) from the fork.
Use it instead of `g_offset_us` in `pll_update()`.

### 3. Presentation-time stall in audio_out_task

Waveshare blocks output in `audio_out_task` until:
```c
server_now_us() >= g_first_present_us + BUFFER_FILL_US - PLAYBACK_LATENCY_US
```
This ensures audio emerges at the server's intended presentation time, eliminating
fixed phase offset between boots/streams. The stall only applies on the FIRST
LOCKED transition per stream; subsequent REACQUIRING→LOCKED transitions skip it.

**Action**: Implement the stall in our `AudioOutput.cpp`. Requires `g_first_present_us`
capture (already in waveshare's `NetworkReceiver.cpp`), `BUFFER_FILL_US`/`PLAYBACK_LATENCY_US`
constants, and a `s_started` flag.

### 4. Rate smoothing IIR may hurt more than help

| | Waveshare | Ours |
|---|-----------|------|
| Phase step | `1.0f + g_rate_ppm * 1e-6f` | `1.0f + rate_ppm_filtered * 1e-6f` |
| Rate filtering | None | IIR, τ=30ms at 48 kHz |

The 30ms resampler rate lag means JB occupancy feedback arrives 30ms late at the
PLL. At 48 kHz, this is ~1440 frames of accumulated error before the PLL sees
any effect. With the PLL running at 200ms ticks, 30ms is 15% of a tick — likely
causing the PLL to overshoot before seeing the correction.

**Action**: Remove `rate_ppm_filtered` IIR from the resampler. Use `g_rate_ppm`
directly (like the waveshare fork). The volatile read is handled by copying to
a local (our existing Change 0 fix).

### 5. sliding-window guard in jb_write prevents wrap corruption

Waveshare checks `frame_seq - s_read_head >= JB_FRAMES` and advances read head
if wrapping would overwrite live data. Required because `s_read_head` is on Core 1
but the writer (wifi_rx) is on Core 0. Without this, long streams can silently
corrupt playback when the write head laps the read head.

**Action**: Add the sliding-window guard to `jb_write()`.

### 6. `__sync_synchronize()` barriers for cross-core JB access

Waveshare uses memory barriers between PCM writes and `valid=true` (producer side)
and between `valid` check and PCM read (consumer side). Our code has no barriers
and `s_read_head`/`s_write_head` are not `volatile`. On the Xtensa architecture,
this can cause the other core to see stale values.

**Action**: Add barriers in `jb_peek()` and `jb_write()`. Make shared heads `volatile`.

## Barge-in speech loss during music playback

### Symptoms
Speech not outputting when server performs barge-in (stop music → speech → resume music).

### Root cause analysis — REVISED

The real race: STREAM_STOP is on port 5006 (control), TTS audio is on port 5005
(audio). UDP on different ports has no ordering guarantee. Audio packets can
arrive BEFORE STREAM_STOP:
1. TTS audio arrives (port 5005) → written to JB, g_mode = MODE_TTS
2. STREAM_STOP arrives (port 5006) → **flushes JB, discarding TTS data from step 1**
3. Remaining TTS audio arrives → may not fill 60ms before stream ends → silence

The waveshare fork avoids this with a **READY packet on the audio port**
(port 5005, same as audio — ordered!). When the server finishes a stream,
it sends READY on the audio port. The READY packet (magic=SYNC_MAGIC, seq=0,
present_us=0) is processed BEFORE any new audio packets on the same port.

**Our project doesn't detect READY.** If a READY packet arrives, our code
treats it as audio (writes 256 silence frames at seq 0), then the next audio
packet causes a sequence gap.

### Fix: READY packet detection in wifi_rx_task

Add READY detection BEFORE the per-packet TTS and magic checks in `wifi_rx_task`:

```c
// READY packet: sequence=0, present_us=0. Server sends this on the audio port
// to signal the current stream is complete and a new one is starting.
// Ordered with audio on the same port → no race with TTS/music packets.
if (pkt.magic == SYNC_MAGIC && pkt.sequence == 0 && pkt.present_us == 0) {
    network_receiver_stream_reset();
    g_state = ST_IDLE;
    jb_flush();
    audio_out_mute();
    continue;
}
```

This must come BEFORE the per-packet TTS high-bit strip and the magic mismatch
check. The READY replaces the STREAM_STOP→STREAM_START race cycle entirely
for barge-in — the server sends READY on the audio port, then starts the new
audio stream. The client processes READY first, then auto-starts on the next
audio packet with per-packet TTS already setting the correct mode.

### Changes (one file, one block)

`NetworkReceiver.cpp:wifi_rx_task()` — insert READY detection after the size
check and before the magic mismatch check:

```c
if ((size_t)n != SYNC_PACKET_SIZE) continue;

// READY packet: ordered on audio port, signals stream completion.
if (pkt.magic == SYNC_MAGIC && pkt.sequence == 0 && pkt.present_us == 0) {
    network_receiver_stream_reset();
    g_state = ST_IDLE;
    jb_flush();
    audio_out_mute();
    continue;
}

if (pkt.magic != SYNC_MAGIC) continue;
// ... rest of audio processing
```
