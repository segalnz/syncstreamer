# Plan: Fix gap handling + TTS startup delay

## Problem 1: Audio deadlock on packet loss

### Root cause
`Resampler.cpp:40-42` — when `jb_peek()` returns nullptr (missing frame), `jb_advance()` is NOT called. The read head stalls permanently at the first gap frame. The crossfade fades to silence over 5ms and **stays at silence forever** because new valid frames are never consumed.

### Fix
Move `jb_advance()` outside the `if/else` so it always executes:
- Valid frame: read prev, advance → normal (unchanged)
- Invalid frame (gap): hold prev sample, advance → 1 frame of sample-hold (~20µs)

At 48kHz, 256 consecutive missing frames = 5.3ms of sample-hold. The existing crossfade (CONCEAL_FADE_FRAMES=240) smoothly dips amplitude to silence and back. Instead of permanent muting, this produces a brief, nearly inaudible level dip.

### File: `lib/syncstreamer/src/Resampler.cpp`
Change the while-loop body to unconditionally call `jb_advance()`:
```c
        jb_frame_t* f = jb_peek();
        if (f) {
            rs->prev[0] = f->pcm[0];
            rs->prev[1] = f->pcm[1];
        } else {
            valid = false;
        }
        jb_advance();
```

## Problem 2: TTS announcements don't play / start too late

### Root cause
`SyncController.cpp:100` — the ACQUIRING→LOCKED transition requires `occ >= JB_STARTUP_FRAMES` (9600 frames = 200ms). Short TTS announcements (1–3 seconds) lose 200–400ms at the start because:
1. The jitter buffer must fill to 200ms before `audio_out_unmute()` is called
2. The sync_task polls at 5 Hz (200ms period), adding up to another 200ms worst-case

The server sends the same `STREAM_START`/audio packets for both TTS and music — there is no server-side TTS signal. Setting `g_mode = MODE_TTS` via the web API happens too late for the first announcement.

### Fix
Play audio during the ACQUIRING state (not just LOCKED/RECOVERING). The resampler naturally outputs zeros until valid frames arrive, so playing during ACQUIRING is safe. This eliminates the startup delay entirely: the first valid frame plays immediately on the next DMA buffer fill.

### File: `lib/syncstreamer/src/AudioOutput.cpp`
Change the play condition at line 96 to include ST_ACQUIRING:
```c
bool play = (g_state == ST_ACQUIRING || g_state == ST_LOCKED || g_state == ST_RECOVERING) && !g_muted;
```

The REACQUIRING path (recovery from underrun) is intentionally excluded — when re-acquiring after an underrun we still want the full buffer before resuming.

## Problem 4: Offset and Filtered err fields show stale/cross-stream values

### Root cause: Offset µs
`g_offset_us = min(present_us - esp_timer_get_time() - 200000)` is the absolute wall-clock difference between the server's Unix epoch timestamp and the ESP32's time-since-boot timer. This is a different huge number every boot (on the order of billions). It's never reset between streams, and worse — the 32-sample rolling minimum retains stale values from the previous stream because new stream timestamps are always larger (monotonically increasing), so the min stays stuck on the old smaller value.

Additionally, `g_offset_us` serves no functional purpose — `server_now_us()` is never called. The only consumer is the status display.

### Fix
#### 4a. `OffsetEstimator.h` — export a reset function
```c
void offset_estimator_reset(void);
```

#### 4b. `OffsetEstimator.cpp` — implement reset (flush ring + zero g_offset_us)
```c
void offset_estimator_reset(void)
{
    for (uint32_t i = 0; i < OFFSET_RING_SIZE; i++) {
        s_ring[i] = INT64_MAX;
    }
    s_idx    = 0;
    s_filled = false;
    g_offset_us = 0;
}
```

#### 4c. `NetworkReceiver.cpp` — call `offset_estimator_reset()` in `network_receiver_stream_reset()`
Add the call alongside the existing seq-gap resets. This ensures the offset ring is cleared every time a stream starts or stops.

### Root cause: Filtered err
`g_filtered_err` is a PLL state variable (`SyncController.cpp:42`). It IS reset on ACQUIRING and REACQUIRING transitions (lines 86, 113). But it is NOT reset on `STREAM_STOP` — the state machine transitions directly to IDLE without going through ACQUIRING/REACQUIRING. If a new stream arrives before the sync_task ticks again (200ms worst-case), the stale filtered_err contaminates the first PLL update.

### Fix
#### 4d. `SyncController.cpp` — reset filtered_err on ST_IDLE entry
The state variable is already reset when entering ACQUIRING. The STREAM_STOP handler in ctrl_rx_task sets `g_state = ST_IDLE`. The next sync_task tick will re-enter ACQUIRING (line 78-91) which resets the error. This is actually already correct for the steady-state case.

BUT — if `ctrl_rx_task` stops the stream during the gap between sync_task ticks, the PLL check in LOCKED/RECOVERING state will use the stale error. This is harmless because the state will immediately switch to IDLE or REACQUIRING.

Actually, re-reading the code: `ctrl_rx_task` sets `g_state = ST_IDLE` and `jb_flush()`. The next sync_task tick calls `state_machine_tick()`, which in ST_IDLE sees `g_stream_active || occ > 0`. After jb_flush(), occ=0. If a STREAM_START also arrived, `g_stream_active=true`, so it transitions to ACQUIRING and resets everything.

**The issue is**: if streams overlap (STREAM_STOP → rapid STREAM_START), the sync_task might not tick in between. On the next tick:
1. `g_state` is ST_IDLE (from STREAM_STOP)
2. It checks `g_stream_active || occ > 0` — if a STREAM_START arrived, `g_stream_active=true`
3. It resets everything including `g_filtered_err = 0.0`

This is correct. The real issue is probably that the **web dashboard shows stale numbers** during the brief IDLE period before the state machine processes the next stream.

No change needed for filtered_err — the existing code already handles it correctly on the ACQUIRING entry. The user likely sees a stale value during the brief interval between streams, which is cosmetic and will self-correct within 200ms.

## Potential additional improvements (low CPU impact)

### 5a. Crossfade smoothing blend — remove low-pass blending
Currently in `Resampler.cpp:73`:
```c
rs->amplitude = rs->amplitude * 0.9f + fade * 0.1f;
```
This IIR blends the target fade with the previous amplitude. At 48kHz with 240-frame fade, the 0.9 coefficient makes the actual fade slower than intended — the amplitude doesn't reach zero until well past 240 frames. Removing the smoothing (direct assignment) makes the fade time match CONCEAL_FADE_FRAMES exactly:
```c
rs->amplitude = fade;
```
This makes gap-induced dips shorter and less noticeable. Low CPU impact (removes one multiply-add per frame).

### 5b. JB_STARTUP_FRAMES for REACQUIRING — reduce to JB_TARGET_FRAMES
Currently REACQUIRING waits for 9600 frames (200ms) before unmuting. After an underrun, the buffer needs to refill to a stable level before resuming playback. But 200ms is conservative — the PLL was already tracking well before the underrun. Reducing to `JB_TARGET_FRAMES` (2880, 60ms) would speed recovery.

However, this increases the risk of immediate re-underrun. The current 200ms is a safe default. Leave as-is unless underrun recovery is observed to be too slow.

### 5c. Enable WIFI_POWER_19_5dBm in main.cpp
Already done (line 54). Good.

### 5d. I2S DMA buffer underrun recovery
`AudioOutput.cpp:110` uses `portMAX_DELAY` on `i2s_channel_write`. If the I2S DMA underruns (buffer empty), the write blocks. When new audio arrives, it resumes naturally. Since `auto_clear=true` (line 33), underrun produces silence. No improvement needed.

### 5e. Remove serial log spam
The serial log_d statement in `sync_task` prints every 200ms. If USB CDC is slow, this can stall the audio task (same core). The `Serial.setTxTimeoutMs(0)` in main.cpp already mitigates this. No change needed.

### 5f. Seq gap detection: only log large gaps 
Already done in `NetworkReceiver.cpp:60-63` — only logs gaps >= 10. No change needed.
